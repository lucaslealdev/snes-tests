# 65C816 test ROM

This is an SNES ROM that performs comprehensive testing of the 65C816 instruction set.

These tests are part of the unified ROM `snes-tests.sfc` (see the README in the root of the repository). In the
menu of the ROM each `*_tests()` function of `make_cpu_tests.py` is one group (one checkbox), and the tests have
tags that the filters of the menu use: *Emulation mode* (tests with E=1), *Undocumented behavior* (tests marked
with `comment=UNDOCUMENTED_COMMENT`) and *Decimal mode* (the decimal groups).

If a test fails, the report of the ROM describes it. For more details see the autogenerated `build/cpu-tests.txt`
and `build/cpu-tests.asm` files. Test numbers are the same in all of them (hexadecimal, `CPU #0123`).

### The ROM tests the following:

- All 65C816 opcodes except STP and WAI
- Each instruction is tested in all supported addressing modes
- Multiple tests per instruction, designed to test edge cases and correct flag result
- Wrapping behavior of various addressing modes for all instructions, with and without emulation mode

### The ROM does *not* test:

- Cycle count taken by instructions, or other timing-related behavior
- Hardware interrupts
- Memory-mapped registers

## Building:

The required tools are ca65/ld65, spcasm and Python 3. Run `make` in the root of the repository: it generates
the tests with `python3 cputest/make_cpu_tests.py build` (add `--plant` for the debug build) and links them with
the harness in `harness/`. There is no option to run a single test: use the menu, which can select the groups.

When changing the generator note that:
- Every check of a test gets an inline stub that records the kind of the check and the expected value before
  jumping to `fail_chk` (harness/runner_cpu.asm), so the report can say which check failed. Use `test()` and the
  addressing mode helpers, and don't write `bne @to_fail` in the extra code; code that finds the wrong path can
  use `bra @to_fail` (a control flow failure).
- A new group must be listed in `add_all_tests()` with `run_group()`.
- The tests must not touch the WRAM used by the runner: run `make check` (`tools/audit_wram.py`).

## FAQ

### How do I find out what a test does?

The autogenerated build/cpu-tests.txt file contains a description of each test, including the input and expected
output register/memory values. For more details, see the autogenerated build/cpu-tests.asm assembly file. To
debug a test, look for its `testXXXX` label (hexadecimal number) in build/snes-tests.map or the label file
build/snes-tests.lbl.

### What undocumented behavior is testsed?

- In emulation mode with S=$1FF, the PLB instruction should read from $200 instead of $100. This is despite
the fact that the CPU manual doesn't list it with the instructions that can access outside the stack page.
- In emulation mode when the low byte of D is nonzero, the (direct,X) addressing mode behaves strangely:  
  The low byte of the indirect address is read from `direct_addr+X+D` without page wrapping (as expected). The high byte is read from `direct_addr+X+D+1`, but the +1 is done *with* wrapping within the page.
  For example: Emulation=1, D=$11A, X=$EE, and the instruction is `lda ($F7,X)`. Here $F7 + $11A + $EE = $2FF. The low byte of the address is read from $2FF and the high byte from $200.
  This behavior only applies to this addressing mode, and not to other indirect modes.
- The behavior of decimal mode isn't fully documented. See appendix A of [this document](http://www.6502.org/tutorials/decimal_mode.html#A) for a full specification.
